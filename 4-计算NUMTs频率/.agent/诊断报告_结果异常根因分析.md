## 二、根因分析

### Bug 1（最高优先级）：单侧 breakpoint 导致合并失效

**位置**：`python/numts_frequency/catalog_utils.py`，`finalize_sample_event_table()` 第 166–177 行

**问题描述**：

`eligible_for_main_analysis` 的判断逻辑为：

```python
has_nuclear = pd.notna(row.nuclear_left_breakpoint_pos) or pd.notna(row.nuclear_right_breakpoint_pos)
```

只要有**任意一侧** nuclear breakpoint 就算 eligible。

**实际数据情况**：

```
breakpoint 文件中 pointGroup 分布：
  nu_Tend_Bleft    2,812,375 行（left breakpoint）
  nu_Tstart_Bright   208,690 行（right breakpoint）
  mt_Tstart        1,034,831 行
  mt_Tend          1,289,980 行
```

left breakpoint 是 right 的 13.5 倍。结果：

- 98,817 个 eligible 事件中，**86,432 个（87.5%）只有 left breakpoint，没有 right breakpoint**
- 这些事件在 `build_distinct_catalog()` 中，`_single_point_or_interval()` 将其处理为单点：`nuclear_merge_start == nuclear_merge_end == left_pos`
- 单点合并时，两个事件若 left breakpoint 相差 >1000 bp 就不会合并，即使它们实际上是同一个 NUMT 插入位点
- 这是 distinct NUMT 数量偏多约 10 倍的**主要原因**

**修复方向**：

在 `build_distinct_catalog()` 中，当 breakpoint 缺失或只有单侧时，**fallback 到 cluster 的 `[cluster_start, cluster_end]` 作为 nuclear 合并区间**。具体逻辑：

```
nuclear_merge_start = nuclear_left_breakpoint_pos  如果有，否则 cluster_start
nuclear_merge_end   = nuclear_right_breakpoint_pos 如果有，否则 cluster_end
如果两者都有，取 [min(left, cluster_start), max(right, cluster_end)]
```

这样每个事件都有一个合理的区间参与合并，而不是退化为单点。

### Bug 2（高优先级）：mt breakpoint span 大量负值

**位置**：`python/numts_frequency/catalog_utils.py`，`finalize_sample_event_table()` 第 133 行

**问题描述**：

```python
merged["mt_breakpoint_span_bp"] = merged["mt_breakpoint_end"] - merged["mt_breakpoint_start"] + 1
```

breakpoint 文件中 `mt_Tstart` 和 `mt_Tend` 是 read 在 mtDNA 上的 T-start/T-end 坐标。**当 NUMT 来自 mtDNA 负链时，Tstart > Tend**（这是生物学上正确的，表示负链方向），导致 span 计算为负数。

**实际数据情况**：

```
eligible 事件中：
  mt_Tstart > mt_Tend（负链）：34,120 个（34.5%）
  mt_Tstart <= mt_Tend（正链）：64,697 个（65.5%）
```

34,120 个事件的 `mt_breakpoint_span_bp` 和 `mt_length_for_main_bp` 均为负数，直接污染了 catalog 的 `median_mt_length_for_main_bp`，导致长度均值为负。

**修复方向**：

```python
merged["mt_breakpoint_span_bp"] = (merged["mt_breakpoint_end"] - merged["mt_breakpoint_start"]).abs() + 1
```

同时，在 `build_distinct_catalog()` 中，mt 合并区间也需要处理方向：

```python
mt_merge_start = min(mt_breakpoint_start, mt_breakpoint_end)
mt_merge_end   = max(mt_breakpoint_start, mt_breakpoint_end)
```

当前代码的 `_single_point_or_interval()` 已经做了 `min/max` 处理，但 `mt_breakpoint_span_bp` 的计算没有取绝对值，需要单独修复。

### Bug 3（中优先级）：not_matched 事件的长度 fallback 不合理

**位置**：`python/numts_frequency/catalog_utils.py`，`finalize_sample_event_table()` 第 138–141 行

**问题描述**：

25,699 个事件在 `merge_bed`（`8-merge_bed.tsv.gz`）中找不到对应记录（`length_bed_match_status == "not_matched"`）。这些事件的长度 fallback 为：

```python
merged["mt_source_span_bp"] = merged["mt_source_span_bp"].fillna(merged["mt_core_span_bp"])
```

其中 `mt_core_span_bp = max(mt_positions) - min(mt_positions) + 1`，而 `mt_positions` 是 cluster 里**所有 reads 的 mtDNA 落点集合**，不是单个 NUMT 片段的长度。

**实际数据情况**：

```
not_matched 事件的 mt_core_span_bp：
  均值：4,526 bp
  >=1000 bp：13,811 个（53.7%）

matched 事件的 mt_source_span_bp：
  均值：335 bp（合理）
```

not_matched 事件的长度严重高估，是长度分布偏长的次要原因。

**修复方向**：

not_matched 事件的长度应优先使用 breakpoint 文件中的 `mt_Tstart`/`mt_Tend` 计算（取绝对值），而不是 `mt_positions` 的 max-min。具体：

```python
# 对 not_matched 事件，用 breakpoint 的 mt span 作为长度
mt_bp_span = (mt_breakpoint_end - mt_breakpoint_start).abs() + 1
mt_source_span_bp = mt_source_span_bp.fillna(mt_bp_span)
# 最后才 fallback 到 mt_core_span_bp（且应加上合理上限，如 16569 bp = mtDNA 全长）
```

### Bug 4（低优先级）：distinct NUMT 代表长度用 median 产生 .5 值

**位置**：`python/numts_frequency/catalog_utils.py`，`build_distinct_catalog()` 第 423–425 行

**问题描述**：

```python
"median_mt_length_for_main_bp": float(sub["mt_length_for_main_bp"].median())
```

对偶数个事件取 median 会产生 .5 值（如 3325.5 bp）。长度本应为整数 bp。

**实际数据情况**：

catalog 中有 595 个 distinct NUMT 的 `median_mt_length_for_main_bp` 含 .5。

**修复方向**：

方案 A（推荐）：用 `mt_primary_fragment_span_bp` 作为代表长度。该字段来自 merge_bed 的主片段（最长的 merged interval），已是整数，语义更清晰。

方案 B：取 median 后 `round()` 转整数：

```python
"representative_mt_length_bp": int(round(sub["mt_length_for_main_bp"].median()))
```
